### 2a. Closing fixes (revision 2) — Cardano indeterminate settlement, payer retry, stale baseline tests
**Cardano indeterminate settlement (was Finding #1; Act Now, release blocker).**
- Before: `src/funding/cardano/adapter.ts` returned `payment_invalid` "settlement_indeterminate: retry with the identical payment header" when settle() timed out and Blockfrost could not yet see the transaction. Core therefore journaled `funding.rejected`, and `clients/payer/payer.ts` automatically re-POSTed the signed funding request on transport failure, 5xx, 429, `facilitator_unavailable` and `settlement_indeterminate`. The canonical unknown-state guard (`service.ts:645-647`) already prevented a second settlement, but rejection semantics, the audit journal and the retry loop all contradicted the intended contract.
- After (adapter, `adapter.ts` `verify()` `!receipt` branch): that exact case returns `{ ok:false, code:'payment_required', settlementAttempted:true }` (the Sui/Solana contract) and logs `settlement.pending_recovery`. Core then keeps the ORIGINAL durable candidate (transaction id, signed header, recovery job, reservation), journals `funding.confirmation_pending` (not `funding.rejected`), and the fund route answers **HTTP 202 `{purchase, confirmationPending:true}`** with `funding: []`. Chain-observed adoption (`recovered_from_chain`), `settlement_pending` receipts, definitive `SettleError`s, `payment_replayed` and every genuine-invalid path are unchanged and still reject. No `payment_invalid` was broadly converted.
- After (payer, `clients/payer/payer.ts`): a run sends **one** signed funding POST. A transport error/timeout, 5xx, 429, legacy `settlement_indeterminate` or a 202 that does not prove evidence is answered by bounded **read-only GETs** of the canonical purchase (`reconcile()`): published evidence → accepted once with that transaction; `awaiting_funding` + `unknown`/`submitted` → **pending** (ledger entry stays `signed`, so cap/daily/cumulative exposure stays counted; nothing marked accepted; no transferReference invented); closed purchase → conflict; nothing observable → fail closed, not retry-safe. A 202 `confirmationPending` with **no funding row** is accepted as pending (previously rejected by this client — the compatibility trap). A payer restart with a held candidate returns pending **without a new challenge, POST or signature**. `facilitator_unavailable` (gateway-proven "settlement never invoked") no longer auto-resends; if canonical state proves nothing was attempted the error is marked retry-safe so a deliberate caller-level repeat resumes the identical stored header. A definitive gateway rejection is still `payment_rejected`.
- Shared plumbing: `clients/payer/bridge.ts` now omits a null `transferReference` (it previously serialized `null`, which the gateway-side `BridgeSuccess` schema would have rejected as `bridge_bad_response`, an existing latent bug on any pending resume); `src/channels/mcp/bridge.ts` also tolerates an explicit null from any payer build.
- Unchanged by design: wallet identity, signed header/digest, ledger history, caps, reservations and recovery; the gateway's one-attempt guard; Sui/Solana.

**Stale baseline tests (was Finding #2; Act Now test maintenance).** Four tests encoded superseded behavior: `postgres.test.ts` hardcoded 12 migrations (13 exist) and three `human-orchestration.test.ts` cases expected quote-time funding filtering. Current design (kept): quotes list configured capability from `acceptedAsset()` without probing any wallet/rail; payment (`createPurchase` → `fundingReady`) checks only the SELECTED source and its dependencies and fails closed (HTTP 503 `route_unavailable`) **before** any purchase/funding obligation exists; fixture-only readiness (`LOCAL_TESTS_ONLY`) cannot be used outside `appEnv='test'`. Tests now assert exactly that, with the real quote-scoped `fundingOptionId` (a fabricated id is a separate 400 test, never the readiness-denial vehicle), a readiness-call counter proving quoting does not probe and payment probes only the selected rail, and the migration count derived from the migration files on disk while keeping the competing-startup, data-preserved and checksum-tamper assertions. No quote-time RPC fan-out was restored and no purchase-time check was weakened. Commit `a0efdb3`.

**Fixtures added** (`tests/unit/cardano-payer-pending.test.ts` 18, `tests/integration/cardano-pending-settlement.test.ts` 5 on disposable native PostgreSQL, `tests/unit/bridge-pending-success.test.ts` 4, plus updated `cardano-adapter` and `cardano-payer` tests): settlement timeout with no chain observation → pending; same transaction later independently confirmed → exactly one funding effect, one `funding_received` journal entry and one merchant execution, settlement invoked once; lost response + payer restart (no challenge/POST/signature, header retained); 202 pending without funding evidence accepted without invented confirmation; no second signed POST after any ambiguous result (counted); same header retained; definitive rejection stays a rejection; cap/daily/cumulative not double-counted; gateway restart recovery; concurrent identical POSTs settle once; canonical state overrides a stale failed handoff (existing `mcp-dual-rail`).
